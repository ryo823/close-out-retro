# close-out-retro

[Claude Code](https://claude.com/claude-code) 向けのスキルです。まとまった作業の終わりに一度だけ走らせる「締めの一手」として、①本当に価値のある学びを記憶（メモリ）とプロジェクトドキュメントの適切な方に振り分け、②作業中に見つかったのに未着手のまま放置されているバグ・課題をissueトラッカーと突き合わせ、③本当に兆候があった場合に限り新規/改善スキル・エージェントの候補を提案します。

English version: [README.md](README.md)

## なぜ作ったか

Claude Codeのセッションでは、「ユーザーからの指摘」「地味だが重要なバグの回避策」「副次的に見つかったのに誰も起票していない課題」「3回も手動で繰り返した手順（本当はスキル化すべきだった）」のような、価値はあるのに端末のスクロールと一緒に消えていきがちな情報が大量に発生します。`close-out-retro`は、こうした情報を「後で思い出す」ことに頼らず、作業の自然な区切りでその場で拾い上げるための、意図的に小さく・呼び出し制の締めのパスです。

フルの監査でも、バックグラウンドで自動発火するフックでもありません。「これで一区切り」というタイミングで、（あなた自身、または「締めよう」的なトリガーフレーズで）明示的に呼び出して使います。

## やること

1. **学びの振り分け: 記憶 vs プロジェクトドキュメント**。残しておく価値のあるものごとに、それが「このユーザー/このプロジェクトと今後どう協働するか」に関する情報（記憶へ）なのか、「コードやシステムそのもの」に関する情報で将来の貢献者（人間でもAIでも）が知って得するもの（`CLAUDE.md`・`docs/*.md`・README等、プロジェクトの正式なドキュメントへ）なのかを判断します。ドキュメントに書いた内容を記憶側に古いまま重複させない、という点も明示的に配慮します。
2. **未着手issueの棚卸し**。セッション中に副次的に見つかったが本題の修正としては直していないバグ・デッドコード・潜在的なエッジケースを、プロジェクトのissueトラッカーと突き合わせ、本当に新規で確認が取れたものだけ起票を提案します。「たぶんバグかもしれない」という推測レベルのものを確定した不具合であるかのように起票しない、という点を明確にしています。
3. **新規/改善スキル・エージェントの提案（本当に兆候があった場合のみ）**。同じ多段階の手順をセッション中に2回以上手動で繰り返した、ユーザーが「毎回面倒」と言った、既存スキルが本来当てはまるはずなのに発火しなかった、といった兆候があるときだけ、候補となるスキル/エージェントを（作成はせず）提案します。プロジェクト固有の知識にどれだけ依存するかでグローバル/プロジェクトスコープを判断します。

詳細な挙動仕様は [`SKILL.md`](SKILL.md) を参照してください。

## インストール

**グローバル**（すべてのプロジェクトで使えるようにする場合）:

```bash
mkdir -p ~/.claude/skills/close-out-retro
curl -o ~/.claude/skills/close-out-retro/SKILL.md \
  https://raw.githubusercontent.com/ryo823/close-out-retro/main/SKILL.md
```

**プロジェクトスコープ**（このリポジトリだけで使う場合）:

```bash
mkdir -p .claude/skills/close-out-retro
curl -o .claude/skills/close-out-retro/SKILL.md \
  https://raw.githubusercontent.com/ryo823/close-out-retro/main/SKILL.md
```

Claude Codeはどちらの場所からもスキルを自動的に読み込みます。ビルドや依存関係のインストールは不要です。

## 使い方

`/close-out-retro` で呼び出すか、作業の終わりに「これで締めよう」「残しておくべき学びある？」「まだ起票してない課題ない？」のように話しかけてください。`SKILL.md`の`when_to_use`はスラッシュコマンドの完全一致ではなく、意図でマッチします。

### 実行例（架空のプロジェクト）

架空のAPIサービス `acme-widgets` にレート制限機能を追加し終えた、というシナリオです。作業中に: ユーザーから設定の置き場所について2回指摘を受け、無関係な不安定テストに気づき、「クォータ確認→設定パッチ→ワーカー再起動→検証→リリースタグ付け」という5ステップの手順を3回手動で繰り返した、とします。

```
> /close-out-retro

## 1. 学び
- [記憶] レート制限の設定は環境変数ではなく`config/limits.yml`に置くのが好み、との
  指摘。理由は「運用チームが再デプロイ無しで制限値を変更できるようにするため」
  （このユーザー/プロジェクト固有のワークフロー方針 → 記憶へ）
- [ドキュメント → CLAUDE.md] ワーカーの再起動順序が重要: 設定パッチを当ててから
  `worker restart`する必要があり、逆順だと1サイクルの間だけ古い制限値が
  静かに残ってしまう。CLAUDE.mdの「レート制限」節への追記を提案。

## 2. 未着手issue
- `test/quota_test.py::test_burst` が今回の変更とは無関係に1回失敗。CI上の
  タイミング起因の不安定テストに見えるが未確認。確定した不具合として起票は
  せず、調査してほしいか判断をお任せします。

## 3. スキル/エージェントの兆候
- 「クォータ確認→設定パッチ→ワーカー再起動→検証→リリースタグ付け」の手順を
  このセッション中に3回手動で繰り返しました。`acme-widgets`固有のワーカー/
  リリースツールに依存するため、プロジェクトスコープのスキル`quota-rollout`
  を提案します。下書きしましょうか？
```

（説明用に作成した架空の例であり、実プロジェクトのデータは使用していません。）

## 設計上の配慮

- **推測を確定したバグとして扱わない**。part 2では「確認が取れて起票すべきもの」と「不安定テストかもしれないので判断はお任せ」を明確に分けています。
- **記憶をドキュメントの古い重複にしない**。`CLAUDE.md`/`docs/`に書かれた内容を、記憶側にただ繰り返すだけのメモとして残さないようにします。
- **スキルは提案するだけで、勝手に作らない**。part 3は常に候補を提示して判断を仰ぐだけで、新しいスキル/エージェントファイルを黙って作成することはありません。
- **そのセッションで実際に出てきたことだけを扱う**。毎回フルのコードベース監査をするわけではありません。

## 関連事例

AIコーディングエージェント自身にセッションの記憶を持たせる試みは、これが最初ではありません。前提として知っておく価値があります。

- [netresearch/retro-skill](https://github.com/netresearch/retro-skill) — セッションの学びを記憶/プロジェクトルール/スキルPRなどの行き先に振り分ける`/retro`コマンド。提案ごとの承認制。このスキルのpart 1にかなり近く、part 3の薄い版（「新規スキル」という行き先バケット）も持つ。issueトラッカーの棚卸し（part 2）はなし。
- [melodykoh/learning-loop-skill](https://github.com/melodykoh/learning-loop-skill) — `CLAUDE.md`/`MEMORY.md`/「Judgment Ledger」へ学びを振り分けるscan/wrap-upの2モード構成。こちらもpart 1に近く、issueトラッカーの棚卸しは無く、スキル/エージェント提案も一級市民の機能ではない。
- [「Claude Codeに『ふりかえり』を教えてみたら、セッションをまたいで成長するAIパートナーに近づいた話」](https://qiita.com/echolimitless/items/949070036dba433c69a9)（Qiita）— セッションのトランスクリプトからパターンを抽出し、繰り返し強化されたものを`CLAUDE.md`や新規スキル/フックへ昇格させる3層の記憶アーキテクチャ。part 1、および閾値ベースのpart 3とかなり重なる。

調べた範囲では、上記のいずれも3点セットを1つのスキルに統合してはいませんでした。特に、作業の副産物として見つかったのに誰も起票していない課題をissueトラッカー側から棚卸しする（part 2）という発想は、かなり珍しいようです。`close-out-retro`は「記憶振り分け（part 1）という発想自体が新しい」とは主張せず、それにissue棚卸しと、作成はせず提案に留める規律あるスキルギャップ検知を組み合わせた統合として位置づけています。
